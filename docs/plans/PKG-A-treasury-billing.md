## 1. الفهم والنطاق واستكشاف الكود الفعلي

### 1.1 الهدف ونطاق العمل
بناء دورة مالية متكاملة وحازمة لمنظومة "عيادتي" متعددة الفروع تبدأ من إصدار الفاتورة عند الحجز أو الكشف، التحصيل بطرق دفع متعددة، ربط كل مليم نقدي بوردية كاشير ودرج محدد، إدارة العجز والزيادة، معالجة الاسترداد والخصومات بحوكمة رقابية صارمة، اشتقاق حالة سداد الحجز، تسجيل رصيد المريض الدائن والمدين، وتوليد أحداث الإيراد `EarningEvent` كعقد مدخلات لمسير أجور الأطباء القادم (F-24/25/26).

### 1.2 داخل النطاق (In-Scope)
- **الفاتورة (`InvoiceModel`):** بنود snapshot غير قابلة للتعديل بعد الإصدار، ترقيم متسلسل بدون فجوات لكل فرع، خصومات بنود وفاتورة بسبب إجباري، بنود ضريبية مرنة (الافتراضي 0%).
- **المدفوعات (`PaymentModel`):** دفعات مجزأة، دفع نقدي مربوط بوردية مفتوحة حصراً، دفع إلكتروني (POS، محافظ، تحويل بنكي)، فائض التحصيل يتحول لرصيد دائن للمريض، منع التكرار (Idempotency).
- **العربون (`Deposit`):** تحصيل مقدم عند الحجز، خصم تلقائي من الفاتورة عند الحضور، سياسة مصادرة أو استرداد مرنة قابلة للضبط عند الإلغاء أو عدم الحضور.
- **الاسترداد (`RefundModel`):** كلي أو جزئي، بسبب إجباري، لا يتجاوز المدفوع، يخصم من الوردية الحالية، الاسترداد بعد قفل اليوم حركة بيوم العمل الحالي.
- **الوردية (`CashierShiftModel`):** درج لكل فرع، رصيد افتتاحي، وردية واحدة مفتوحة للكاشير لكل درج، يوم عمل (`businessDate`) يمتد عبر منتصف الليل، إغلاق أعمى اختياري، تسليم عهدة، إعادة فتح مشروطة، قفل اليوم (`closeBranchDay`).
- **حركات النقدية (`CashMovementModel`):** مصروف نثري، إيداع بنكي، سحب مالك، عهدة إضافية (الحد الأدنى من F-21).
- **رصيد المريض (`PatientBalanceModel`):** مديونيات فواتير، رصيد دائن، كشف حساب حركات، سداد مديونية (الحد الأدنى من F-20 لكل فرع).
- **الإيصالات والتقارير:** إيصال حراري 80 مم و A4/A5 بترويسة الفرع وعلامة "نسخة" عند إعادة الطباعة، تقرير الوردية Z-report، تقرير تحصيل اليوم، أعمار الديون.
- **توليد أحداث الإيراد (`EarningEvent`):** إنشاء أحداث مدفوعات واستردادات مفصلة على مستوى البنود والأطباء المنفذين لتغذية احتساب الرواتب.

### 1.3 خارج النطاق موثقاً (Out-of-Scope)
- **مطالبات التأمين وشركات الرعاية (F-23):** فواتير التأمين ونسب التحمل والخصم التعاقدي ستُبنى بالكامل في F-23.
- **الموردون والمشتريات وإدارة المخازن والمصروفات الشاملة (F-21):** يقتصر النطاق هنا على الحركات النقدية المباشرة في الدرج (Petty Cash Movements).
- **بيع الصيدلية والأدوية للجمهور (F-40):** الخزينة تخدم خدمات وعيادات المنشأة فقط حالياً.
- **التكامل مع منظومة الفاتورة والإيصال الإلكتروني الحكومي (ETA E-Invoice / E-Receipt):** ⚠️ **خطر امتثال قانوني وضريبي**: متطلبات منظومة الضرائب المصرية (توقيع إلكتروني، تشفير HSM، بنية UUID، إرسال فوري إلى ETA API) تتطلب استشارة وموافقة محاسب قانوني معتمد ومكتب ضرائب. لا تُبنى افتراضياً ولا يُفترض شكلها برمجياً في هذا الإصدار، ولكن صُمم هيكل الفاتورة والأرقام التسلسلية والتصنيفات بحيث تكون جاهزة للربط عبر Middleware لاحقاً دون كسر قاعدة البيانات.

## 2. القرارات المعمارية والتصميمية الإلزامية

### 2.1 كلاس القيمة المالي `Money` (قروش صحيحة)
```dart
class Money {
  final int piastres; // 100 قرش = 1 جنيه مصري
  const Money(this.piastres);
  const Money.zero() : piastres = 0;

  factory Money.fromPounds(num pounds) => Money((pounds * 100).round());
  double toPounds() => piastres / 100.0;
  String toDisplay() => '${(piastres / 100.0).toStringAsFixed(2)} ج.م';

  Money operator +(Money other) => Money(piastres + other.piastres);
  Money operator -(Money other) => Money(piastres - other.piastres);
  Money operator *(num factor) => Money((piastres * factor).round());
  bool operator <(Money other) => piastres < other.piastres;
  bool operator <=(Money other) => piastres <= other.piastres;
  bool operator >(Money other) => piastres > other.piastres;
  bool operator >=(Money other) => piastres >= other.piastres;
}
```

### 2.2 الفاتورة (`InvoiceModel`) ودورة حياتها
- **حالات الفاتورة:**
  - `draft`: مسودة مفتوحة لتجميع الخدمات والإجراءات، **بدون رقم متسلسل**.
  - `issued`: فاتورة معتمدة صادرة، **تحصل على رقم تسلسلي فريد للفرع فور الإصدار**، غير قابلة للتعديل نهائياً.
  - `partially_paid`: مسددة جزئياً ومتبقي مديونية.
  - `paid`: مسددة بالكامل.
  - `refunded`: مستردة كلياً أو جزئياً عبر إشعارات دائنة.
  - `voided`: ملغاة (فقط إذا كانت مسودة أو صدرت ولم يُسجل عليها أي سداد أو حركة درج نهائياً).
- **ترقيم متسلسل بدون فجوات (Gapless Numbering):**
  - صيغة الترقيم: `INV-{BRANCH_CODE}-{YEAR}-{000001}` (مثلاً: `INV-CAI-2026-000142`).
  - الترقيم لا يُحجز عند فتح المسودة؛ بل يُسند في اللحظة الذرية (Atomic transaction) لاعتماد الفاتورة (`issueInvoice`). في حال إلغاء مسودة قبل إصدارها، لا تضيع أرقام من المتسلسلة.
- **بنود الفاتورة كـ Snapshot كامل:**
  - كل بند `InvoiceLineItemModel` يحفظ: `serviceId`, `serviceName` (نص وقت الإصدار), `unitPricePiastres`, `quantity`, `category`, `performingDoctorId`, `discountPiastres`, `totalPiastres`.
  - تغيير سعر الخدمة أو حذفها لاحقاً من الكتالوج لا يؤثر على الفاتورة التاريخية إطلاقاً.
- **حوكمة الخصومات والضرائب:**
  - الخصم إما نسبة مئوية أو مبلغ ثابت بقروش محددة، مع **حقل سبب إجباري**.
  - فحص الصلاحية: `StaffPermissionEnum.applyManualDiscount`.
  - حد الإعفاء التلقائي: خصم حتى 10% أو 10,000 قرش (100 ج.م) يمرره موظف الاستقبال/الكاشير. أي خصم أعلى يتطلب اعتماد المدير (`approveDiscount`).
  - الضريبة: حقول قابلة للضبط لكل بند (الافتراضي: 0%).

### 2.3 التحصيل والورديات والدرج الناري (Strict Shift Constraint)
1. **التحصيل النقدي (`PaymentMethodEnum.cash`):**
   - **قاعدة صارمة:** لا يمكن تسجيل أي دفعة نقدية على الإطلاق إلا إذا كان المستخدم الحالي لديه **وردية مفتوحة نشطة (`open`) لنفس الفرع ومرتبطة بدرج نقدية (`registerId`)**.
   - إذا حاول المستخدم تحصيل نقدية بدون وردية: الشاشة تمنعه وتظهر زر "فتح وردية كاشير جديدة أولاً".
2. **التحصيل غير النقدي (`card_pos`, `wallet`, `bank_transfer`, `receivable`):**
   - يُسجل مباشرة على الفاتورة مع حقل `referenceNumber` إجباري (رقم عملية الـ POS، كود التحويل، رقم محفظة فودافون كاش).
   - لا يدخل في رصيد النقدية الفعلي لدرج الكاشير؛ بل يُسجل في عمود منفصل بتقرير الوردية لتسويته مع كشف الحساب البنكي أو إيصال ماكينة الدفع.
3. **منع التكرار (Idempotency):**
   - كل طلب تحصيل يولد معرّف معاملة فريد `clientTransactionId` (UUID) عند فتح نافذة الدفع، ويبقى ثابتاً لنفس المحاولة.
   - إذا تم الضغط مرتين بسرعة على زر "تأكيد التحصيل"، المستودع يفحص الـ ID ويرفض المعاملة المكررة فوراً مع إرجاع الدفعة المسجلة الأولى.

### 2.4 العربون والاسترداد
- **العربون (`Deposit`):**
  - يُسجل كـ `PaymentModel` من نوع `deposit` مرتبط بـ `bookingId`.
  - عند إصدار الفاتورة عند الحضور، يُحتسب العربون كدفعة مقدمة تُخصم فوراً من إجمالي الفاتورة المطلوب.
  - في حال إلغاء الحجز: تطبق سياسة الفرع (إما رد العربون بحركة استرداد أو مصادرته وتحويله لإيراد عدم حضور).
- **الاسترداد (`Refund`):**
  - لا يمكن استرداد مبلغ أكبر من إجمالي المسدد على الفاتورة.
  - كل استرداد يرتبط بـ `originalPaymentId` ويشترط سبباً إجبارياً وصلاحية `refundPayment`.
  - إذا كان الاسترداد بعد إغلاق يوم العمل للفرع: **يُمنع منعاً باتاً تعديل اليوم المقفول**؛ ويسجل الاسترداد كحركة سحب نقدية في الوردية المفتوحة ليوم العمل الحالي مع الإشارة إلى رقم الفاتورة الأصلية.

### 2.5 إدارة الورديات وقفل يوم الفرع
- **فتح الوردية:** يسجل الكاشير الرصيد الافتتاحي (العهدة النقدية بالدرج).
- **تاريخ يوم العمل (`businessDate`):** يتحدد لحظة فتح الوردية (مثلاً: 2026-11-09). إذا امتدت الوردية لما بعد منتصف الليل، تظل تابعة لنفس الـ `businessDate` لضمان صحة التسويات اليومية.
- **حركات النقدية النثرية (Petty Cash Movements):** إمكانية إدخال/إخراج نقدية من الدرج لأسباب تشغيلية (مصروف نثري، شراء أدوات، إيداع، سحب أرباح) مع تسجيل البيان والمستلم والصلاحية `manageCashMovements`.
- **الإغلاق الفعلي والعجز/الزيادة:**
  - عند القفل، يقوم الكاشير بعدّ النقدية الفعلية وإدخالها.
  - خيار "الإغلاق الأعمى" (Blind Close): إخفاء المبلغ المتوقع عن الكاشير لضمان دقة العد ونزاهته.
  - النظام يحسب الفرق: `الفارق = الفعلي - (الافتتاحي + المقبوضات النقدية + الدخول - المدفوعات النقدية - المصروفات)`.
  - أي فارق يتجاوز الحد المسموح (مثلاً 50 ج.م) يطلق تنبيهاً ويطلب إدخال تبرير إلزامي.
- **قفل يوم الفرع (`closeBranchDay`):** إجراء يومي ينفذه مدير الفرع أو المحاسب لإقفال كافة ورديات اليوم وتثبيت المركز المالي للفرع، ويمنع بعده أي حركة بأثر رجعي.

### 2.6 رصيد المريض والمديونيات (F-20 Minimum)
- **مستوى الرصيد:** يُسجل ويُحسب **لكل فرع على حدة** (`patient_branch_balance`)، مع توفير بطاقة مجمعة على مستوى المنشأة في ملف المريض تعرض تفصيل رصيده بكل فرع.
  - *التبرير:* الفروع كيانات تشغيلية ومالية منفصلة بحسابات وورديات وضرائب مستقلة؛ وخلط مديونيات الفروع بدون تسوية بينية (Inter-company settlement) يسبب فوضى محاسبية.
- **الفائض:** أي دفع يتجاوز إجمالي الفاتورة يتحول فوراً إلى رصيد دائن للمريض في هذا الفرع، ويمكن استخدامه كطريقة دفع في الفواتير المستقبلية (`use_credit_balance`).

### 2.7 اشتقاق حالة دفع الحجز بدون كسر الاختبارات
- يتم استبدال الحقل اليدوي في شاشات الحجز بقيمة **مشتقة محسوبة برمجياً (Derived Getter)**:
```dart
PaymentStatusEnum get derivedPaymentStatus {
  if (invoice == null) return paymentStatus ?? PaymentStatusEnum.unpaid;
  if (invoice!.outstandingPiastres <= 0 && invoice!.paidPiastres > 0) {
    return PaymentStatusEnum.paid;
  }
  if (invoice!.paidPiastres > 0) {
    return PaymentStatusEnum.partiallyPaid;
  }
  return PaymentStatusEnum.unpaid;
}
```
- الحجوزات التجريبية السابقة (الـ 7 حجوزات المسددة في `BookingsMockRepoImpl`) يتم زراعة فواتير مسددة متطابقة لها في الذاكرة بنفس المعرفات، مما يحافظ على نجاح الـ 119+ اختباراً القائمة بنسبة 100% دون تعديل أي assertion سابق.

## 5. الشاشات وواجهات المستخدم والتدفقات (UI Flows)

### 5.1 الشاشة الرئيسية للخزينة (`CashierPage` - `/cashier`)
- **الهيدر التفاعلي:** حالة الوردية الحالية للمستخدم (مفتوحة / مغلقة)، اسم الدرج، الرصيد النقدي اللحظي، وأزرار سريعة: "فتح وردية"، "قفل الوردية"، "حركة نقدية"، "تقرير اليوم".
- **شريط المؤشرات المالية (KPI Summary Cards):**
  1. إجمالي مقبوضات اليوم (نقدي + إلكتروني).
  2. النقدية في الدرج (Cash in Drawer).
  3. المقبوضات الإلكترونية (POS & Wallets).
  4. إجمالي المديونيات غير المحصلة.
- **تبويبات الشاشة الرئيسية (4 Tabs):**
  - **التبويب 1: فواتير اليوم (Invoices Tab):** جدول فواتير الفرع، بحث بالاسم ورقم الفاتورة، فلترة بحالة السداد، زر إنشاء فاتورة، إجراءات سريعة (تحصيل، استعراض، طباعة، إشعار دائن).
  - **التبويب 2: ورديات الكاشير (Shifts Tab):** استعراض الورديات، الفارق (عجز/زيادة)، طباعة تقرير Z، زر إغلاق الوردية الحالية.
  - **التبويب 3: حركات الدرج النقدية (Cash Movements Tab):** جدول المصروفات النثرية والإيداعات والسحوبات.
  - **التبويب 4: رصيد المريض والمديونيات (Patient Balances Tab):** كشف المديونيات المعلقة وإمكانية السداد السريع.

### 5.2 حوارات العمليات الأساسية (Dialogs)
1. **حوار فتح الوردية (`OpenShiftDialog`):** إدخال العهدة الافتتاحية، اختيار الدرج، وتأكيد تاريخ يوم العمل.
2. **حوار قفل الوردية (`CloseShiftDialog`):** إدخال النقدية الفعلية بعد الجرد (مع خيار القفل الأعمى)، حساب الفارق آلياً، إدخال سبب الفارق إن وجد، وطباعة Z-Report فوراً.
3. **حوار التحصيل (`CollectPaymentDialog`):** استعراض المبلغ المتبقي، تحديد المبلغ المدفوع، اختيار طريقة الدفع، إدخال المرجع، والتحقق التلقائي من الوردية النقدية المفتوحة.
4. **حوار تسجيل حركة نقدية (`AddCashMovementDialog`):** تحديد النوع (مصروف نثري/سحب/إيداع)، المبلغ، السبب، والمستلم.
5. **حوار الاسترداد والإلغاء (`RefundInvoiceDialog`):** تحديد البنود والمبلغ المسترد، اختيار سبب الاسترداد الإلزامي، ومطالبة موافقة المدير إذا تجاوز الحد.

## 6. أمثلة اختبارية يدوية مفصلة ومحسوبة بالقروش (≥ 25 مثالاً)

| # | السيناريو المالي والتشغيلي | الحسابات الرياضية المباشرة (بالقروش) | القيمة الناتجة والحالة المتوقعة |
| :--- | :--- | :--- | :--- |
| **1** | فاتورة كشف باطنة 250 ج.م بدون خصم | `250 * 100 = 25,000` قرش | الإجمالي: 25,000 قرش، المتبقي: 25,000 قرش (`issued`) |
| **2** | سداد كامل نقدي لفاتورة كشف 250 ج.م بوردية مفتوحة | رصيد الدرج السابق: 50,000 قرش + 25,000 قرش | رصيد الدرج: 75,000 قرش، حالة الفاتورة: `paid` |
| **3** | محاولة سداد نقدي بدون وردية كاشير مفتوحة | فحص `activeShift == null` | **رفض العملية فوراً** برسالة خطأ توجب فتح الوردية |
| **4** | خصم مبلغ 50 ج.م على كشف 300 ج.م بسبب معتمد | `30,000 - 5,000 = 25,000` قرش (الخصم 16.6%) | يمر للمدير للاعتماد (`approveDiscount`) لاجتيازه 10% |
| **5** | خصم نسبة 5% على كشف 400 ج.م | `40,000 * 0.05 = 2,000` قرش (20 ج.م) | يمرر تلقائياً بواسطة الاستقبال (أقل من حد 10%) |
| **6** | دفع جزئي 150 ج.م لفاتورة إجماليها 400 ج.م | المدفوع: 15,000 قرش، المتبقي: `40,000 - 15,000 = 25,000` قرش | حالة الفاتورة: `partially_paid`، المديونية: 25,000 قرش |
| **7** | استكمال سداد متبقي فاتورة مدفوعة جزئياً (250 ج.م) | المدفوع السابق: 15,000 + 25,000 = 40,000 قرش | حالة الفاتورة تتحول إلى `paid`، المتبقي: 0 |
| **8** | دفع زائد (Overpayment): مريض يدفع 500 ج.م لفاتورة 450 ج.م | الفاتورة: 45,000 قرش، المقبوض: 50,000 قرش | الفاتورة: `paid`، **رصيد دائن للمريض**: 5,000 قرش (50 ج.م) |
| **9** | استخدام رصيد المريض الدائن لسداد فاتورة جديدة 100 ج.م | رصيد المريض الدائن: 5,000 قرش، المطلوب: 10,000 قرش | يخصم 5,000 من الرصيد، ويدفع المريض 5,000 نقداً |

| **12** | إلغاء حجز بعربون مع سياسة "استرداد كامل" | استرداد العربون: 10,000 قرش من الدرج | خصم 10,000 قرش من درج الوردية النشطة |

| **25** | ضغط مزدوج متزامن على زر "تحصيل" (Idempotency Test) | إرسال طلبين بنفس الـ `clientTransactionId` في نفس اللحظة | الطلب الأول ينفذ، الطلب الثاني يرجع نتيجة الأول دون تكرار |

## 7. أحداث الإيراد `EarningEvent` (عقد الرواتب F-24/25/26)

عند كل عملية تحصيل أو استرداد، يولد المستودع حدث إيراد غير قابل للتعديل:
```dart
class EarningEvent {
  final String id;
  final String invoiceId;
  final String lineItemId;
  final String branchId;
  final String performingDoctorId;
  final List<String> assistingStaffIds;
  final int amountPiastres;
  final EarningEventTypeEnum eventType; // collection | refund
  final DateTime occurredAt;
  final String paymentId;
}
```
- **قاعدة توزيع الدفع الجزئي على البنود:**
  - تطبق قاعدة **أولوية الإجراءات الطبية والمستهلكات أولاً، ثم كشف الطبيب (Waterfall Rule)**: يتم سداد تكلفة الإجراءات والخدمات المنفذة بالكامل أولاً لضمان تغطية تكاليف العيادة والمستهلكات، ثم يُوجّه باقي المبلغ لخدمة كشف الطبيب.
